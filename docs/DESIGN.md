# DESIGN.md — 골든 룰

이 문서는 리포지터리의 **핵심 신념과 불변 조건**입니다. 위반 시 그에 맞는 오류 메시지를
만들어 에이전트 컨텍스트에 수정 지침을 주입할 수 있어야 합니다.

## 골든 룰

1. **경계에서 파싱한다** (parse, don't validate).
   - 외부 경계(IO, 네트워크, 설정, 저장소)에서 들어오는 데이터는 추측하지 말고 검증된 형태로 파싱.
   - 내부에서 "형태를 가정"하는 코드는 버그의 온상. 타입 안전하게 강제하거나 SDK로 위임.
2. **공유 유틸리티를 선호한다**.
   - 불변 조건을 중앙에서 관리하기 위해 직접 만든 임시 헬퍼보다 공유 유틸리티 패키지를 우선.
   - 필요한 경우 자체 구현은 유닛 테스트 100% 커버리지를 요구한다.
3. **"YOLO-style" 탐색 금지**.
   - 추측한 형태로 데이터를 사용하지 말 것. 스키마/타입을 먼저 정의하라.
4. **교차 관심사는 Providers로만**.
   - 인증, 커넥터, 텔레메트리, 기능 플래그는 명시적 인터페이스로만 유입.
5. **레이어 단방향성**.
   - `Types → Config → Repo → Service → Runtime → UI` 밖으로 역류 금지.
6. **문서는 코드와 동기화**.
   - 코드가 바뀌면 문서도 바뀐다. 드리프트는 스테일 문서(수정 PR 대상).

## 취향 (인간이 아닌 에이전트 기준)

- 결과물이 "인간의 문체 취향"과 달라도 됨. 정확하고, 유지 가능하고, 다음 에이전트 실행에서
  읽기 쉬우면 충분.
- 취향이 코드에 반영되어야 할 만큼 반복되면 **규칙을 도구로 승격**(린터)하라.
- "지루한" 기술(결합성 낮고, API 안정적이고, 학습 설정이 명시적인 것)을 선호.

## 실패 시 대응

- 규칙 위반 발견 → 즉시 수정하거나, `docs/exec-plans/tech-debt-tracker.md`에 기록.
- 문서로 옮겨야 하는 규칙이 자꾸 나오면 → 도구(스크립트/린터)로 승격.
